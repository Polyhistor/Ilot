3 Scaffold Approaches

All use Next.js App Router + Supabase + Vercel. The difference is how the data layer and routing are structured. Pick the one that fits best.

A

Supabase Client Direct

Data layer: Query Supabase directly from Next.js Server Components using @supabase/ssr. No ORM, no extra abstraction. Data fetching happens at the page/component level.

Routes: /[category]/[slug] with generateStaticParams for ISR.

Pros

  • Simplest setup
  • Official Supabase + Next.js pattern
  • Least boilerplate

Cons

  • SQL queries scattered across components
  • Harder to swap DB later
B ★

Supabase + Repository Layer Recommended

Data layer: A thin lib/db/ repository layer wraps all Supabase calls. Components and pages call functions like getServiceBySlug() — never raw SQL. Clean separation.

Routes: /[category]/[slug] with ISR. API routes at /api/services power future admin panel.

Pros

  • Clean architecture
  • API routes ready for custom admin later
  • Easy to test & swap DB
  • Scales naturally

Cons

  • Slightly more files upfront
C

Supabase + Prisma ORM

Data layer: Prisma ORM sits between Next.js and Supabase. Type-safe schema, auto-generated client, migrations tracked in code.

Routes: Same as B. Prisma schema doubles as the source of truth for DB structure.

Pros

  • Full type-safety
  • Schema-as-code migrations
  • Great DX for complex queries

Cons

  • Heavier setup
  • Cold start latency on Vercel
  • Overkill for this scale

I recommend B — clean now, ready for the custom admin later. Click or reply in the terminal.
